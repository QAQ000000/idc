# 有界商品刷新与完整快照发布（2026-11-10）

**后续客户接入**：客户本地预览已另批接入，默认关闭；有效快照的组合在本站后端计价，checkout仍在线复核。本页保留刷新批历史验收边界，当前M2范围及误删恢复限制见[客户契约](M2_LOCAL_PREVIEW.md)。

## 冻结范围与兼容

本批承接[插件对价验证](M2_LOCAL_PRICING.md)，新增明确范围的自动采样、完整校验、版本化发布和独立计划运行模板。**客户仍使用原在线calculate／checkout，不启用客户本地预览。** 没有真实购买、自动退款或Worker执行变化。389仅只读对价，563仍保留零库存门禁；不为刷新导入新商品。

完整价格规则通过可选 `SnapshotRulesDriverInterface` 交给具体插件校验。核心只调用契约，魔方库存／倍率／价格矩阵语义仍在插件。原ProductSnapshotService由CLI、管理员和刷新服务共用；无新表、列、迁移或价格树副本，27表保持。

## 有界范围与运行

在目标环境唯一配置中显式指定 `PRODUCT_REFRESH_IDS=本地ID1,本地ID2`，最多50个不同的正整数ID；空值默认停用，非法值拒绝，不自动扫描全目录，不把远端商品ID当本地ID。只选择这些已存在、非retired且上游启用的本地商品；hidden也可刷新，但不会自动上架。连接／账号／商品绑定不能被刷新替换。

`php artisan products:refresh` 每次最多2个商品，按最早尝试时间、ID排序；每个商品至少10分钟才可再次尝试，成功和失败均计入。相邻商品开始前间隔1秒，逐个执行，不并行放大上游请求。每批在开始下一商品前检查60秒预算；**已经开始的单商品允许完成**，不能宣称每批严格60秒。原驱动每请求12秒总超时，两周期完整读／报价／复读共10次请求，网络等待最多约120秒；可选systemd服务另有240秒进程上限。

整批持有非阻塞MySQL `GET_LOCK`，名称按库隔离，不依赖Redis租约。第二进程立即返回overlap_skipped，进程崩溃／连接消失后锁自动释放。发布事务再次核对原连接ID和锁所有者；不能在重连后的新会话继续发布。锁只协调可丢失的刷新工作，不参与资金或资源占用。

10分钟是同商品的最小尝试间隔，不是全范围刷新时限。按每分钟最多2个计算，50个商品轮询至少25分钟，慢请求还会延长；启用范围应按实际耗时收敛，未轮到或已过期商品继续在线核价。

## 准备与完整发布

上游读取均在事务外。使用现有商品绑定、名称、类别、加价、已售周期与当前默认配置，不静默新增周期或替换失效选项。默认配置无法通过新规则时保留旧快照，交管理员处理。

准备过程：

1. 原驱动读取配置，原ConfigOptions校验枚举联动和数量选择。
2. 每个已配置周期执行原完整在线预检，首期／续费成本与售价分开取得；库存仅更新原Redis观察，不覆盖本地配额。
3. 可选完整规则契约要求币种、全矩阵、周期、阶梯、生成规则和价格政策完整，插件计价器在默认组合分别与在线首期／续费对价。任何周期不支持或不一致，整次失败，禁止部分发布。局部默认组合对价不等于全部组合真实验收。
4. 再读一次完整配置，对比剔除明确库存观察后的内容；读取期间规则变化则拒绝。不能完全消除供应商在最后读取之后变化的窗口，客户提交和Worker仍实时预检。
5. 同一数据库事务锁定原商品与上游，重核开始前的商品销售字段、快照、绑定、连接身份和最新管理员商品审计。改名、改价、上下架、刷新或ABA编辑均使旧准备失效；本地配额消耗不算管理员编辑。
6. 经原persist整体替换当前配置、联动、全部原始价格规则、默认配置与两类参考价格；同时提交成功观察。失败／异常回滚，历史账单、实例冻结价、原订单namespace和Outbox不动。

不支持完整计价规则的旧商品保留原快照，客户继续原在线核价；不会用默认组合价格或部分矩阵凑成“完整刷新成功”。在线失败仍无可成交报价。

## 内容版本与观察分离

魔方 `snapshotContent()` 只剔除明确的products.stock_control／qty／upstream_stock_control／upstream_qty；未知字段保守保留，不默认认为不影响销售。首次新保存的schema不写这四个观察字段；旧快照在无内容变化时不为清理库存字段而重写，比较时同样剔除。已有库存继续使用独立Redis五分钟观察。

原config_cache仍是销售快照，新增整数 `snapshot_revision`：首次新快照为1，实际内容变化时递增，旧快照缺省为0。内容比较递归规范化对象键顺序，保留列表顺序；配置、联动、数量范围／步长／区间、完整价格规则、生成规则、默认配置和本地参考售价仍参与。相同内容不执行商品UPDATE；实际变更后再改回旧内容也不会复活旧报价。

客户报价仍用原完整config_cache签名，不替换成诊断pricing_hash。相同内容的计划刷新不改变报价／管理员版本；改价、加价规则等仍由原版本检查保护。管理员显式刷新原审计仍正常追加，管理员版本因此变化，不宣称人工操作无审计。

运行观察复用 `system_settings` 的独立 `product.refresh.<本地ID>` 行（group=catalog）：last_attempt_at、result、finished_at、last_success_at、valid_until、snapshot_hash及固定失败reason。Unix秒均代表UTC；只记录最后一次结果，不新增永久历史副本。启动时先记running，中断后保留未完成记录；下一次到达重试间隔再重新采样。成功后有效期900秒；失败保留最后成功及其原有效期，不延长新鲜度。

管理员详情增加只读 `snapshot_refresh`，返回结果、尝试／成功／失效时间、fresh及固定pricing_mode=online。只有观察hash匹配当前快照且未过期，fresh才为true；改价后旧成功观察不会误标新快照新鲜。观察时间／结果不进入config_cache、报价指纹或管理员编辑版本。

本批所有客户报价本来就走在线，故快照过期或完整规则不支持仍在线核价；在线失败不会退成本地参考价。fresh不是本地价格授权。缺配置／损坏且无法渲染时原商品异常保护继续生效，不能声称任意损坏都可继续销售。

## 独立计划模板与启用

不把长上游调用放进原财务 `schedule:run`，也不在其oneshot cgroup内启动可能被清理的后台子进程。扩展原渲染器的可选参数，默认仍只生成原四个unit：

```bash
python3 scripts/render_systemd.py --name jianyun-prod \
  --app /srv/jianyun/current --php /usr/bin/php8.4 --user jianyun \
  --env-file /etc/jianyun/runtime.env --output /tmp/jianyun-prod-units \
  --product-refresh
systemd-analyze verify /tmp/jianyun-prod-units/*
```

新增 `NAME-products.service`（oneshot、240秒上限）和 `NAME-products.timer`（分钟唤起、Persistent）；同一service运行中timer不会叠加实例，CLI手动重叠仍有MySQL锁保护。十分钟业务间隔与批次范围唯一在ProductRefreshService，不复制为第二个业务cron。无需新常驻Worker。

按运行规程核对环境后，**只安装这两个可选unit**，daemon-reload并启用NAME-products.timer；不能因渲染输出含原四个unit就覆盖、重启其他服务。唯一env配置启用ID，已有配置缓存按同环境重建；空ID保持关闭。日常通过 `journalctl -u NAME-products.service`、`systemctl status NAME-products.timer`及管理员详情观察；失败输出固定原因／商品ID，不记录连接地址、凭据或原始响应。每商品失败会继续本批其他候选并记录warning，命令正常结束不代表全部刷新成功。

停用时停止／禁用本环境products.timer，再停止其products.service；中断只留旧快照与running观察，不能借此修改任务或资金。M2／正式启用另按运行验收安排，本批不自动选商品或安装M2单元。
