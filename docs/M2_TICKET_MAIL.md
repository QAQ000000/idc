# 工单邮件提醒

## 范围与产品行为

新工单首条消息、客户追加回复通知显式配置的管理员；管理员公开回复通知工单所属客户。每个收件人单独占位，邮件仅有更新提示、工单编号及需登录的本站工单链接（定位最新回复），不复制主题、正文、客户邮箱、实例/IP、密码、业务凭据或免登Token。客户／管理员仍使用各自的主会话与原归属校验。

结单只追加原关闭记录和审计，不进入普通消息通知分支；不会通过中文内容判断事件。即使普通消息恰好使用结单措辞，仍按普通消息处理。内部便签／转派／附件未开放，不扩展通知场景。工单邮件不操作资金、资源或履约任务。

## 来源、启用起点与防重

TicketService仅在成功插入新的普通消息后，调用TicketNotificationService，在**原消息事务**内写入notification_deliveries；结果未知时重试原请求，返回原消息与原占位，不重复生成。此处只有短SQL，没有SMTP调用，不让消息提交与通知占位发生提交后丢失。若本地占位写入失败，消息事务一同回滚，客户可用原请求键重试；外部发送失败不回滚已提交会话。沿用原27表，无新字段、迁移、事件表或队列。

订阅配置存system_settings的`notify.ticket_mail`，与`notify.mail`的SMTP密文和原任务／临期／重置配置分离。默认未配置即关闭。只有邮件总开关和工单开关同时启用，新消息才占位。工单开关、指定管理员ID、服务端生成activation及activated_at（UTC）同事务保存与审计；调用方不能填写历史起点。

启用起点是**配置提交后取得该配置共享锁的消息事务**。消息持共享配置锁到提交，配置使用排他锁：先于启用观察到关闭的消息不占位；等待启用提交的消息可按新配置占位。每次显式启用、停用或改接收人均生成新activation，旧排队消息在发送前失效，不跨订阅期补发。没有工单来源扫描／补扫，不扫描历史回复，也不复用正文或时间戳推断旧事件。原notifications:sweep只恢复发送未知状态及补扫既有任务／临期来源。

指纹：`ticket:{ticket_id}:reply:{reply_id}:admin:{admin_id}`或`ticket:{ticket_id}:reply:{reply_id}:user:{user_id}`；`UNIQUE(fingerprint,channel)`继续物理防重，activation不进入指纹，不能通过重新启用重发同一事件。不同管理员即使共用邮箱仍是不同收件身份；应只配置需要通知的管理员。

context仅冻结kind=ticket_update、ticket_id、reply_id、customer_id、author_type／author_id、activation，无正文副本。复用原target保存占位时的邮箱，不自动改地址。

## 发送与并发边界

独立mail Worker复用原pending→sending认领、SMTP结果CAS、超时转pending_manual_check及超级管理员证据核验；绝不重发未知请求。认领前按收件人→工单→原回复→当前配置→通知行的顺序重核：工单原归属、来源为原公开消息和原作者、收件身份／启用状态／原邮箱、当前指定管理员、activation和邮件总开关。原SMTP配置入口只调整总渠道，不覆盖工单订阅。旧或失配占位保留failed／STALE_BUSINESS_CONTEXT，不重定向、不删除重建。允许原普通消息在工单随后关闭后发送提示，关闭本身不触发消息。

原工单写锁序为作者→工单→消息→共享配置；配置是超级管理员→指定管理员→渠道／订阅配置。回复占位的外键检查也可能取得收件人行锁，因此客户／管理员同时回复或与发送器竞争可能发生数据库死锁；SQL事务最多3次死锁重试，全部消息与占位一起回滚重试，SMTP在认领提交后才调用，不能在可重试事务内发送。共享配置锁增加短暂数据库读锁，配置修改可能等待在途消息提交；未增加全局消息处理器或持久游标。网络发送期间的账号／邮箱变化无法撤回已被SMTP接受的邮件；内容不含会话正文，最终权限以站内登录为准。

## 配置与运行

沿用同环境PHP、APP_KEY和数据库，通过本地CLI／私有stdin及当前启用super_admin操作；没有网页订阅管理或客户自选偏好：

```bash
php artisan notifications:tickets ADMIN_ID < /受保护目录/ticket-mail.json
```

输入：`{"enabled":true,"admin_ids":[1]}`；停用：`{"enabled":false,"admin_ids":[]}`。启用要求已有邮件总渠道配置且开启；命令返回服务端生成的activation、activated_at与指定管理员ID，同事务追加ticket_notification_configure审计。输入不能携带SMTP密钥、渠道、历史回复ID或activation。再次执行会切换订阅期并使旧排队消息失效，应作为显式运营动作。

首次运行需先有000009工单字段；本批无新迁移。更新代码后按[运行规程](DEPLOYMENT_RUNTIME.md)核对并优雅重启本环境mail Worker，使其加载ticket_update认领分支，再显式开启订阅。业务Outbox Worker无需改动或重启。既有PHP-FPM按原发布流程加载新代码，不替换共享服务。未开启前不得以测试名义给真实客户发信。
