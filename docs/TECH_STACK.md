## 2. 框架与领域职责

Laravel 承接通用基础设施；定价、账单、钱包、退款、返佣、实例生命周期和未知结果恢复继续由领域服务按现有契约实现。HTTP Controller 负责接收、校验和调用服务；具体 Provider、支付、通知与验证码插件通过契约和注册器装配，核心不直接依赖具体插件。

迁移必须保留以下约束：

- 正常云消费的账单 CAS、余额扣款、资金账本、收款记录及 Outbox 入库使用**同一物理数据库连接、同一事务**。现有 PDO SQL 可以通过框架管理的连接适配，不要求全部重写为 ORM。
- 数据库事务与外部调用分开；业务幂等、任务令牌/租约和人工核验门禁继续按 [TASKS_OUTBOX.md](TASKS_OUTBOX.md) 执行。Laravel 普通队列、`afterCommit` 或任务重试设置均不能替代持久 Outbox 和未知结果调查。
- Redis 唤醒可以丢失，MySQL 扫描必须兜底；Redis 锁或租约到期不能解除实例业务占用。
- 用户/管理员身份隔离、API 归属校验和模拟登录限制继续保留。现有 Token 与 AES-256-GCM 密文格式需要兼容；引入框架认证或加密组件前核准格式、主密钥及存量数据的转换，不能直接替换后丢失解密能力。
- 后台 Worker 为独立受管理进程；逐任务隔离用户、请求与事务状态，并验证崩溃、重启及过期执行者回写。HTTP 使用 PHP-FPM 也不免除 Worker 的常驻状态管理。

现有文档中的 `Database::transaction()` 等示例表达领域事务边界，框架适配时统一连接和事务管理，不要求永久保留自建路由、Redis 协议客户端等基础代码。

## 3. 数据库与插件兼容

完整 DDL 继续以 [database/schema.sql](../database/schema.sql) 为唯一事实来源，当前 **8 张核心表、26 张物理表**基准及保护触发器继续有效。Laravel 默认迁移中的用户、会话、缓存、队列等表逐项审查，不能重复建立用户/账本/任务模型；合适的基础设施数据可使用已选 Redis。

schema 迁移运行器及其版本登记方式在实施阶段明确。若确需新增迁移元数据或其他物理表，必须先完成领域/基础设施边界审查，并同步数据库设计、权威 DDL、接口影响及路线图，不能以框架默认行为跳过表数基准。本文不新增表、不改变字段或外键。

旧站数据迁移工具仍是**独立上传旧站的导出插件**，输出指定目标版本的 SQL 数据库备份，通过通用 MySQL 工具恢复空库。它不成为 Laravel 模块或简云插件；目标 schema 变化后重新生成导出包并演练，详见 [MIGRATION_RUNBOOK.md](MIGRATION_RUNBOOK.md)。

## 4. UI 与交付节奏

统一使用 Element Plus 标准组件与一套布局；前端保持 Vue Router、Pinia 和现有 REST API 组织，不因采用 Laravel 自动切为 Inertia 或增加第二套前端。Tailwind 不是首版必需依赖，少量业务样式按需添加。组件、状态、权限与响应式规则见 [FRONTEND.md](FRONTEND.md)。

首条真实链路以一个上游、一个商品和一个支付渠道完成“购买 → 收款 → Outbox → 真实交付 → 实例查看”，带必要管理及异常核验入口。随后扩展续费与日常运营，再逐项增加上游和增值功能。各阶段使用真实接口完成必要页面；界面精修排在业务闭环之后，财务安全及生产门禁不因缩小范围而降低。
