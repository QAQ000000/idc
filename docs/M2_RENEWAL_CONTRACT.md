# M2 后续：同上游固定商品续费（2026-11-08）

## 变更原因与边界

首条真实新购已在 `290c9b7` 验收。本批在同一 Worker、付款服务和实例页面上增加一个原账期的续费，不新增表、不扩展通用配置或第二个上游，不强迫新购驱动实现续费。原新购请求及付款接口保持兼容。

`RenewalDriverInterface` 是明确可选能力；首个实现为魔方财务。增加只读预检、一次续费执行及只读续费调查。核心只引用 `app/Plugins` 契约，协议及自动解挂差异留在具体插件。

## 账单、付款与周期

- `POST /instances/{id}/renew` 必须带当前看到的 `base_due_date`（UTC 秒精度字符串），只买一个原 `billing_cycle`。同周期请求重放返回原单，包括付款和交付之后，不能变成下一次购买；月/年付不通过任意月份参数互换。
- `cycle_marker=r:{instance_id}:{原到期日YYYYmmddHHMMSS}` 保留已付周期的唯一凭证。未付取消、不可逆销毁保护退款同步清空标记；续费取消不销毁原实例、不返还新购库存。
- 固定本地报价取 `COALESCE(override_price,recurring_price)`，`quote_expired_at=NULL`。出账前只读预检上游账号范围资产、商品、账期、续费价格及上游原/目标到期日，并要求上游自身自动续费关闭，避免两套代扣并行；不产生上游账单、不扣款。上游成本与本地售价值分别冻结，预检不改实例固定售价。
- 同一实例锁下，账单 `unpaid -> paid` CAS、钱包扣款或渠道实收凭证、累计消费、从**原本地到期日**顺延一个自然月/年，以及唯一 `renew` Outbox 同事务提交。月末/闰年夹紧；日期快照统一秒精度，避免 MySQL 参数运算的微秒表示破坏比较。
- 本地已购权益与上游履约分开。上游采用其账户接口返回的原日期和单周期 duration，不能把本地新购交付确认时刻强行覆盖上游既有日期。执行前日期/价格变化停止自动推进；未知结果只读反查目标日期，不再生成上游账单或再次付款。
- 相同网关交易回调不二次收款；不同真实重复款、过期归属或非销毁门禁的实收只入钱包，不二次顺延。不可逆/主动销毁时，未付续费单按 SC-L02 一次转 refunded、释放周期标记，实收仅一笔 refund_to_balance；没有实际扣款的余额/代扣请求不凭空退款。

## 暂停、销毁与恢复

本批自动流程支持 active 和 suspended/billing。魔方收取续费款可能自动发起解除暂停，且客户端不能可靠区分上游暂停原因，因此对 compliance/abuse/manual 暂停采取**拒绝自动续费并交人工处理**的当前策略；不会用支付绕过风控。未来若支持保留暂停的续费，必须先验证具体驱动能保留上游安全状态。

欠费暂停付款后保持 suspended，任务中冻结 `needs_unsuspend=true`。魔方插件在同一 renew 执行中付款后观察上游到期日和 Active；没有确认恢复则保持调查和本地暂停，不假设成功，也不拆分可乱序领取的独立 unsuspend 任务。超过观察窗口进入人工门禁。

只有 pending 且 termination_reason=billing_overdue 的销毁任务能在正常续费付款事务中取消，递增令牌并保留终止标记；运行中、调查中、人工核验的销毁即使租约已过期仍阻断；主动退订和安全销毁不撤销。其他未决任务与云消费退款冻结继续使用现有 TaskGate。

人工裁决允许在证据、旧令牌、enabled super_admin 门禁下重试或确认原资产续费完成；不接受把续费资产换成另一个 ID。新购的 cancel_compensate 不复用于续费，避免终止原有付费资源；续费扣款成功而上游未成功时只通知管理员核验，不自动退款或撤回本地权益；未知结果先调查。退款由管理员手动办理，自动退款/补偿与网关退款调用不属于当前交付范围，见 [人工退款策略](PAYMENTS_LEDGER.md#manual-refund-policy)。

## 出账、代扣与部署

`renewals:generate` 每小时扫描提前 7 天及已到期、仍具备续费条件的资源，只创建/返回唯一未付账单。`renewals:debit` 每 15 分钟独立扫描，持锁重检 auto_renew、窗口、实例/任务/退款门禁和余额；钱不够保留原单，后续充值后下一次扫描可继续。关闭自动续费不影响手动付款。

这两个命令只登记到 Laravel 调度，不安装系统 cron，不修改生产配置。充值提交后已增加下述异步唤醒；15 分钟 MySQL 扫描仍是恢复路径。轮询按 ID 分页，避免前一批阻断订单长期饿死后续订单。实际调用上游仍由现有 outbox:work 独立执行。

## 续费异常通知与人工核验（2026-11-08）

**策略定案**：用户确认续费扣款成功而上游未成功时，通知管理员处理即可，不需要自动退款。本批不增加续费补偿入口、原到期日回滚、退款账本或资源销毁逻辑；新购 cancel_compensate 仍仅处理未交付新购，不能用于原续费资源。已支付凭证、原账单、记账权益和资源保持完整，不能因接口超时推定未履约或自行退款。

### 当前通知方式

沿用已存在的 Worker 告警日志及 `php artisan outbox:inspect` 待核验任务列表。首次续费执行未获 succeeded（包含明确未执行后的安全退避）在任务事务提交后记录 warning：`Paid renewal requires upstream verification`，携带 task_id、invoice_id、instance_id、action、execution_token、状态及脱敏结果码。只读调查的每分钟未知结果不重复刷 warning；确证未执行后再次执行若仍异常，可记录该次执行的 warning。到达人工门禁记录 critical：`Outbox manual review required`，同样含定位字段。成功没有异常通知。

任务持久状态是待办事实，日志是原通知出口；事务回滚不发告警。数据库提交与日志输出不是原子投递，进程恰在两者之间崩溃或日志被丢弃时，仍须通过 inspect 列表/日志监控值守，不能宣称已必达管理员。当前 CLI inspect 最多返回前 100 条未决任务，网页 /admin/tasks 已提供分页。单邮件补扫已覆盖 failed + MANUAL_AUDIT_REQUIRED，复用通知表异步告警；首次异常 warning 仍只记日志，未进入人工核验不发邮件。Telegram 与其他通知场景延期，SMTP 未知不重发，详见 [通知契约](NOTIFICATIONS.md)。部署侧须确保 Worker stderr 被采集及待办被巡检，本批不修改生产日志服务。

### 调查与回填

未知沿用同一任务 investigating 只读查询，不重发续费、付款或解挂，不自动退款。超过观察窗口转 failed + MANUAL_AUDIT_REQUIRED 后，继续保留业务占用、告警并交管理员核验。确认已续费只通过调查成功或原有 fulfill 回填，不再累加到期日；确认不能履约由管理员联系上游及用户处理，程序不自动移动资金。

人工 `resolve` 新增续费专用 `action=investigate`：需启用 super_admin、当前 expected_execution_token 和 10–1000 字符 evidence。仅已付 renew、failed + MANUAL_AUDIT_REQUIRED、原资源仍存在、其他 blocker/退款门禁通过时可受理。在同一事务内将任务恢复 investigating、递增 token、清 Worker/租约/退避时间、开始新观察窗口并追加 task_investigate 审计；保留原 payload 的冻结身份/日期、retry_count 及 upstream_task_id。下次 Worker 只调用 queryRenewal，不走 renew；旧 Worker 不得覆盖裁决。没有 confirmed_no_execution 要求，因为此动作不会重发业务请求。retry/fulfill 的既有权限及证据要求保持不变。

```json
{
  "action": "investigate",
  "expected_execution_token": 7,
  "evidence": "工单编号：上游查询已恢复，继续核验原续费单"
}
```

入口仍为 `POST /api/v1/admin/tasks/{id}/resolve`，或 `php artisan outbox:resolve TASK_ID ADMIN_ID < resolution.json`。没有新增退款 action。单邮件核验告警已交付，其他推送及非财务暂停自动处理保持待办；充值唤醒见下述独立增量。

## 充值到账后的异步唤醒

用户于 2026-11-08 授权补齐充值提前触发自动续费；只处理该客户符合条件的原续费单，不自动出新账单，不改变原自动续费授权、报价、账期或异常处理策略。若另行验收真实上游，只限已验收的体验 CDN（商品 391），不续费 VPS 或重新购买资源；本轮隔离协议验收不作为真实付款证据。

正常充值的唯一实收、账单 CAS、钱包和 recharge 流水先在原事务中提交。LedgerService 仅在新增正向 recharge 流水后登记框架 afterCommit，最外层提交完成才发送 Redis SADD 客户 ID 提示；嵌套或外层回滚不发送。afterCommit 只用于可丢失的提前扫描提示，不能承载扣款、续费权益或 renew Outbox。迟到／额外实收、取消补偿和钱包消费不触发本批提示，仍按原用途记账和原定时策略处理。

复用现有 outbox:work 循环，每轮先 SPOP 一个客户，再通过 RenewalService::debitDue(userId) 扫描本人原单，随后继续原 Outbox 执行。集合按环境密钥摘要及数据库名隔离，只含客户 ID；相同客户并发充值可合并，也允许消费提示后又收到一条新提示。既不依靠提示次数认定收款，也不把弹出提示视为业务完成。没有新表、队列实体、调度频率或额外守护进程；原每 15 分钟全库扫描保持。

每张候选仍由原 BillingService::pay(..., automatic=true) 持锁重查 auto_renew、提前 7 天窗口、实例／账单归属、原价格／周期、任务／退款／销毁门禁、账户状态和余额。续费账单 CAS、钱包扣款与流水、原到期日顺延及唯一 renew Outbox 同事务；不同唤醒与定时器竞争只会结算一次。关自动续费、余额不足、取消／旧周期、非财务暂停、退款冻结和过期租约的未知任务都不放行，不重置 Worker 执行令牌。

回调不扫描续费单、不调用上游；正常响应确认的是原充值入账。Redis 发布／消费失败记录脱敏 warning，并在该进程退避 60 秒后再访问，不让已提交充值变成付款失败，也不阻断原 Outbox 执行。提示发布失败、消费后崩溃或 Redis 数据丢失都由 15 分钟 MySQL 扫描收敛；扣款／任务事务失败也不丢原未付账单。Redis 沿用现有有界连接超时，提示不能替代 MySQL 业务占用。

本批目标是更早启动原单处理，不承诺严格秒级或上游完成时间：Worker 繁忙／正在网络调用、客户原单积压或 Redis 故障均可能延后；页面继续按本单真实任务展示交付／调查／人工核验。无需数据库迁移；部署时须重启目标环境原 Worker 加载循环，HTTP 与 Worker 使用相同 APP_KEY、数据库及 Redis 配置。更新前旧 Worker 不消费提示，原扫描继续生效，回退仅失去提前唤醒，不回滚充值或已付续费事实。

影响 LedgerService、RenewalWakeupService、RenewalService 和 Artisan Worker 循环。并发到账验收还暴露原收款 SQL 事务在不同充值单竞争时可能死锁回滚：Database::transaction 增加可选尝试次数（默认仍为 1），仅 PaymentService 的已验签 SQL 结算显式最多尝试 5 次，由框架对数据库并发冲突完整回滚后重试，不重发外部请求；普通业务异常和重试耗尽仍交原失败／网关重试路径。验证包含在账本插入时注入一次死锁后，凭证、余额和流水仅一份、只有最终提交发布提示。

支付验签接口、Provider 插件、上游调用、资金规则或任务事实保持原契约。摘要、API、账本、数据库字典、运行规程及路线图同步，无 schema／历史数据迁移。新增成本仅为一个可丢失 Redis 客户集合和原 Worker 每轮一次非阻塞弹出，不引入消息实体、额外进程或第二套代扣逻辑。
